# f0_deception — production deployment (single VPS)

## Prerequisites

- A public VPS with **ports 80, 443, 53/udp and 2525/tcp** free
- Docker + docker compose plugin
- A domain you control:
  - `*.tokens.yourdomain.com` A record → your VPS IP (wildcard)
  - NS delegation or a hosted zone the gateway can answer for DNS tokens:
    simplest is an A wildcard plus the gateway answering authoritative
    queries on :53 for `tokens.yourdomain.com`
  - MX record for `alerts.yourdomain.com` → your VPS (email tokens only)
  - `console.yourdomain.com` A record → your VPS IP

## Deploy

```sh
cd deploy
cp .env.example .env
$EDITOR .env          # fill in domains/IP
docker compose up -d --build
```

Services:

| Service | Ports | Purpose |
|---|---|---|
| `gateway` | 80, 53/udp, 2525 | catches token triggers (HTTP/DNS/email) |
| `console` | 443, 8080 | web console + API proxy (Caddy, auto-TLS) |
| `api` | internal | REST API + SQLite (`api-data` volume) |

Open `https://<CONSOLE_DOMAIN>` and create your first token.

## Notes & hardening TODOs

- Token trigger URLs generated by v1 use `F0_GATEWAY_ORIGIN`; set it to
  `https://...` only if Caddy also terminates TLS for token hostnames —
  otherwise use `http://` (trigger URLs embedded in documents should ideally
  be HTTPS; wildcard-cert TLS for token hosts is on the roadmap).
- Email tokens: for production, prefer publishing :25 directly
  (`F0_SMTP_PORT=25`) or fronting with Postfix → relay to :2525.
- Back up the `api-data` volume; it holds all token/incident history.
